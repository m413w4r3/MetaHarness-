## Cause confirmée

rapport parce que l'identifiant configuré est `claude-opus-5.5`, avec un point.
Opus 5.5 existe : le sélecteur interactif fourni par l'utilisateur le montre.
L'exécutable Claude Code installé (2.1.284) contient l'identifiant
`claude-opus-5-5`, avec des tirets, et son aide accepte également l'alias
`opus`. Le message de refus générique ne prouve pas une absence du modèle.

Preuves dans `../MetaHarness-runs/20260928T135523Z-85b255f156/` :

  model (claude-opus-5.5). It may not exist or you may not have access to it. »

  fixent le profil `claude-opus-5-medium` avec le modèle `claude-opus-5.5`.

  `last_green_commit=15f80e9eabeba215177bb53c68547bb053cb33ff`.

  n'est présent dans la passe examinée.

`examples/autowork.toml:258` configurait précisément cet identifiant erroné
pour le profil d'audit par défaut. La configuration est désormais corrigée
en `claude-opus-5-5`, sans changement du nom du profil ni de l'effort.

## Pourquoi le diagnostic affiché est trompeur

`src/metaharness/agent/execution.py:_result` normalise déjà le résultat en
`status=failed`. Il privilégie actuellement `terminal_is_error` et attribue
`AGENT_PROTOCOL_FAILED`, même lorsque le processus sort avec le code 1.

`src/metaharness/orchestration/audit.py:159` ignore ensuite le statut,
`exit_reason`, `backend_reason`, le timeout et le code de sortie. Il parse
directement `final_message` comme un bloc `META AUDIT v1`, puis remplace le
diagnostic par « audit report is missing or malformed ».

Le classifieur Claude ne reconnaît actuellement que des signaux
d'authentification. Le refus de modèle n'a pas de diagnostic dédié.

Enfin, `web/pages.py` et `web/static/run.js` affichent « Waiting for external
authorization » pour tout état `waiting_external`, y compris ce problème de
configuration. Aucune demande d'autorisation n'apparaît dans la réponse agent.

## Correction appliquée et améliorations proposées

Correction appliquée : `examples/autowork.toml` utilise l'identifiant exact
`claude-opus-5-5`. Les améliorations de diagnostic ci-dessous restent des
propositions ; elles ne sont pas nécessaires pour corriger la faute de
syntaxe du modèle.

1. Dans l'adaptateur, classifier le refus de modèle avec un diagnostic borné
   et expurgé, puis produire un motif générique d'échec d'exécution.
   Réserver l'échec du protocole d'audit à une exécution réussie dont le bloc
   est absent ou invalide. Préserver le traitement spécifique des autres
   erreurs terminales, notamment la limite de tours ; ne pas reclassifier
   toutes les erreurs Claude à partir de ce seul exemple.
2. Dans `AuditService.run`, après le contrôle de HEAD et avant le parseur,
   contrôler le résultat normalisé : timeout, échec de démarrage ou
   d'exécution, authentification et autres erreurs terminales. Remonter le
   motif et un diagnostic utile via la voie de redaction existante. Ne jamais
   accepter un rapport même syntaxiquement valide si l'exécution a échoué.
   Garder le contrôle de l'ownership Git prioritaire.
3. Afficher un libellé générique pour `WAIT_EXTERNAL`, avec le motif réel
   et l'action pertinente : corriger la disponibilité ou la configuration
   du profil, puis reprendre l'audit.
4. Valider l'exécution avec le runtime géré lors de la reprise, en utilisant
   l'identifiant corrigé. Aucun fallback implicite n'est ajouté.

Cette correction conserve l'autorité d'audit unique et le gate après audit
exigés par C7 de la spec v4. Elle ne transforme pas un échec d'infrastructure
en `DONE`, `NEEDS_WORK` ou `SPEC_DECISION`.
