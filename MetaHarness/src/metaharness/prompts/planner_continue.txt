EMBEDDED META PLAN v2
The plan covers the next milestone only, never the whole project, and is
compiled for {{MAX_STEPS}} steps at most ({{LAST_STEP_ID}}). One step is one
testable, coherent unit with one observable result and one targeted
verification, and 1 to {{SINGLE_STEP_MAX_PATHS}} mutable paths by default for a
SINGLE plan, 1 to {{STAGED_STEP_MAX_PATHS}} per step for STAGED (the union of
WRITE_SET, CREATE_SET and DELETE_SET). A step may exceed that default only for
a genuinely atomic transformation, and CONTEXT must then explain the
atomicity. Never return a BLOCKED plan here: an under-specified SPEC is a
SPEC_DECISION, and a large milestone is planned with the rest named in
PROJECT_REMAINDER.
Every step must leave lint and type-check no worse than before it: the
harness checks the whole repository after each step. A change that breaks
existing code (new required field or parameter, renamed symbol, changed
signature or return type) is one atomic transformation with every affected
call site and fixture: put them in the same step, list them in WRITE_SET, and
explain the atomicity in CONTEXT. Never plan a later step to repair callers
an earlier step broke.
VERIFY must pass as soon as its own step ends: never list a check, test or
command that only passes after a later step.
DEPENDS_ON names an earlier step only when this step really needs code that
step creates or changes (a symbol, file, fixture or test it reads, imports or
extends); otherwise it is NONE. Point at the step that produces what is used,
never merely at the previous step. A failed step skips every step that
depends on it, so an unnecessary dependency turns one failure into an empty
iteration.
A REASONING or AGENTIC step carries exactly one responsibility: when its
INSTRUCTIONS cover several independent concerns (for example a hash, a
reference scheme and a timeline), split them into separate steps. Target
at most 6 numbered operations for REASONING and AGENTIC steps. A genuinely
atomic change with 7 to 12 operations needs an `ATOMIC_SCOPE:` line in CONTEXT
explaining why splitting it would break an intermediate repository state.
Target about 4000 characters for these contracts; the upper part of the range
is for MECHANICAL steps and atomic call-site lists.
Shared source or test files do not justify merging independent responsibilities.
Separate independently validated domain objects, and separate structural
validation from serialization when each can pass a targeted check alone.
A milestone delivers one subject. Two independent subjects are two
milestones: plan the first and name the second in PROJECT_REMAINDER.
Keep premium audit work bounded: persistence, reuse/revision, workflow cutover,
invalidation and frontend delivery are separate milestones when independently
verifiable. Do not pack them into one milestone merely because they concern
the same feature. Keep a truly atomic API cutover and its callers together.
Before removing or renaming a symbol, enumerate its importers and coupled
test doubles/fixtures; update them in the same step and verify test collection.
Use executable targeted behavioral checks in VERIFY. Do not leave predictable
fixture migrations or broken imports for the premium auditor to discover.

Each step is a compact, localized, directly executable contract with no minimum
length. Aim below 4000 characters; hard limit {{MAX_STEP_CONTRACT_CHARS}}.
Do not paste existing source, full files, logs, the SPEC or repeat requirements
across fields. The worker reads its READ_SET locally: point to existing symbols
instead of copying their definitions. CONTEXT carries the
repository facts the worker cannot derive. INSTRUCTIONS holds 1 to 12
numbered concrete operations. INTERFACES names the exact signatures, types and
invariants to produce or preserve. EXAMPLES is one reduced excerpt or NONE.
TESTS names the behaviors to pin. PITFALLS lists what a low-cost executor gets
wrong. DONE_WHEN and VERIFY are observable. Each step uses at most
{{MAX_READ_PATHS_PER_STEP}} unique READ_SET paths written as
`- relative/path :: exact symbol`, with no wildcards and no absolute paths.
For deterministic serialization, specify canonical UUID/date/enum wire forms
and tests that reject noncanonical forms. VERIFY should name only focused
checks for that step; the harness owns the repository-wide gates.
EXECUTION_CLASS is MECHANICAL, REASONING or AGENTIC, chosen from the difficulty
of the step.
